# 단계 1 — 보유 이력서에서 공고 검색까지

## 목표

사용자가 자신의 이력서를 등록하고 추출한 내용을 확인하면, 그 경력을 근거로 찾은 공고를 볼 수 있게 구현해줘. 새로고침과 서버·worker 재시작 후에도 문서·확정 경력·검색 작업·결과를 다시 읽을 수 있어야 해.

## 읽을 자료

CLAUDE.md, docs/PRODUCT_SPEC.md, docs/UI_UX.md의 등록·확인·추천 화면, docs/ARCHITECTURE.md, contracts/v0.7/README.md와 등록·확정 사실·SearchIntent·작업 계약, docs/ACCEPTANCE.md의 해당 항목을 읽어줘. 기존 코드 위치는 CODEMAP으로 좁혀줘.

## 구현

1. **소유권과 저장**: 기존 workspace/session을 확인하고 v0.7 principal 소유 관계를 연결해줘. 서버가 인증한 소유 범위로 원본·추출·확정 사실·검색 결과를 조회하게 해줘. 클라이언트의 owner ID만 믿지 말아줘. 로컬 개발 세션과 운영 사용자 인증의 범위를 구분해줘.
2. **DB 변경**: v0.4 파일은 유지하고 v0.7 추가 migration을 명시적으로 연결해줘. 기존 전체 객체 hash 검증·metadata를 migration 버전에 맞게 갱신해줘. 기존 DB를 지우거나 자동 reset하지 말아줘.
3. **입력 경로**: 텍스트 PDF 등록을 먼저 구현하고 텍스트 붙여넣기 경로도 제공해줘. 파일 크기·MIME·추출 가능 여부를 확인하고 원본 bytes hash·소유자·상태를 보관해줘. 스캔 PDF·미지원 DOCX·빈 추출은 명확히 안내해줘.
4. **추출·확인**: 원문 페이지 또는 텍스트 구간에 연결된 경력 후보를 보여줘. 사용자의 수정과 확인을 거쳐 확정 사실 revision을 만들어줘. 희망 직무·지역·급여 등은 경력 사실과 별도 조건으로 저장해줘.
5. **검색 계획**: 확정 경력의 역할·기술·책임과 사용자 선호에서 SearchIntent를 생성해줘. 연락처·이메일·불필요한 개인정보는 검색 질의에 넣지 말아줘. 확정 경력·조건 revision을 요청에 고정해줘.
6. **작업과 worker**: 요청을 idempotent하게 저장하고 작업 claim·lease·generation을 검증해 mock 어댑터를 실행해줘. 네트워크/모델 호출은 DB transaction 밖에서 수행하고 결과 저장 시 작업 소유권을 다시 확인해줘.
7. **공고 표시**: 저장된 공고·출처·추천 이유·미확인 조건을 화면에서 조회해줘. 후보 없음·부분 실패·처리 중·재시작 복구를 구분하고, 정보 없음과 조건 미충족을 다르게 표현해줘.
8. **fixture**: `fixtures/resumes/`의 합성 파일을 실제 업로드 경로로 검증해줘. 서로 다른 역할의 이력서가 다른 SearchIntent를 만들게 해줘. 기존의 항상 같은 공고를 반환하는 preview를 이 제품 경로의 완료 증거로 사용하지 말아줘.

## 완료 기준

- 텍스트 PDF와 텍스트 입력으로 원본→확정 사실→검색→저장 결과가 이어진다.
- 추출 실패를 빈 경력 성공으로 저장하지 않는다. 확인 전 경력을 확정 검색 근거로 사용하지 않는다.
- 역할·기술이 다른 이력서 두 개의 검색 계획과 설명이 달라진다.
- 다른 소유자의 문서·추출·결과에 접근하면 거절한다.
- 중복 요청·재시작·만료 lease·오래된 결과가 데이터 손실이나 최신 화면 덮어쓰기를 만들지 않는다.
- mock 표시와 실제 source provenance를 유지한다. Liner live 호출은 별도 구현·검증 상태로 남긴다.

관련 코드 테스트·계약 검사·typecheck·필요한 build와 실제 HTTP/UI 확인을 수행해줘. 브라우저를 사용할 수 없으면 실제 관찰 미실행을 명시하고 가능한 서비스 경계 검증을 완료해줘. 이번 결과와 다음 미완료 작업을 docs/state에 기록해줘. S01만 끝났다면 S02 검색 연결을 이어가고, 제품 단계 1 전체 완료를 확인한 뒤 대화·PDF 단계로 이동해줘.

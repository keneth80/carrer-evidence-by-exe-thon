# Claude Code 전달용 — 제품 흐름 정정

Career Evidence의 제품 흐름을 아래 사용자 의도에 맞게 수정해줘. 먼저 현재 저장소·미커밋 변경·구현 상태를 읽고, 이미 만든 기능을 재사용해줘. 기존 v0.5 파일을 일괄 재생성하거나 v0.4 계약을 그대로 덮어쓰지 말아줘.

## 제품 목표

1. 사용자가 이미 가진 이력서 파일을 등록한다.
2. 원본에서 경력을 추출하고 사용자가 내용을 확인한다.
3. 확정 경력·역할·기술과 사용자 조건으로 공고를 검색해 보여준다.
4. 사용자가 공고를 선택하면 AI와 대화하며 해당 공고에 맞는 이력서를 수정한다.
5. 변경 비교·미리보기를 거쳐 제출용 파일 버전을 확정한다.
6. Ego 또는 Chrome 실행기로 해당 파일을 첨부하고 지원한다.
7. 지원 공고·제출 이력서 버전·답변·접수 근거·진행 상태를 기록한다.
8. 사용자가 별도로 설정한 정책 안에서 유사 공고의 이력서 준비와 자동 지원을 실행할 수 있게 한다.

FLOW_REVIEW.md, DECISIONS.md, ACCEPTANCE.md를 읽고 기존 CLAUDE.md·구현 계획·CODEMAP·PROGRESS·HANDOFF·첫 프롬프트를 위 흐름과 맞춰줘. 이 문서의 자동 지원 예시 값은 실행 승인으로 취급하지 말아줘.

## 현재 범위와 차이를 확인

기존 fixture 선택·React 고정 query·3개 합성 공고·샘플 PDF 첨부는 개발 예제다. 실제 이력서 업로드·경력 추출·대화형 문서 수정·공고별 PDF 생성·실제 지원 완료로 표시하지 말아줘.

기존 source/fact/evaluation, worker/lease, immutable revision, 파일 hash, 지원 기록 구조는 재사용해줘. 새로운 계약은 별도 버전과 명시적 migration으로 만들고, 기존 v0.4 baseline과 회귀 테스트는 보존해줘. 현재 DB를 삭제하거나 자동 reset하지 말아줘.

## 이번 세션의 첫 구현 목표

**이력서 등록 → 추출 결과 확인 → 확정 경력 revision → 이력서에서 만든 검색 계획 → 저장된 검색 작업 → 공고 노출**을 한 흐름으로 구현하고 검증해줘.

1. 입력 형식과 현재 파서 의존성을 확인해 텍스트 PDF를 먼저 지원하고, 추출 실패 시 텍스트 붙여넣기 경로를 제공해줘. 이미 DOCX 지원이 있으면 유지해줘. 스캔 PDF를 정상 추출로 가장하지 말아줘.
2. 원본 bytes hash·소유 범위·추출 상태·원문 페이지/구간을 보존하고, 사용자가 확정한 경력만 검색 입력에 사용해줘.
3. 경력 사실과 희망 조건을 분리하고, 수정 시 revision을 새로 만들어줘.
4. SearchIntent를 경력의 직무·기술·역할에서 생성해줘. 연락처 등 불필요한 개인정보를 검색 질의에 넣지 말아줘. query를 React로 고정하지 말아줘.
5. 기존 세션/context/task/worker가 구현돼 있으면 연결하고, 없으면 이 흐름에 필요한 부분을 추가해줘.
6. mock으로도 실제 업로드·추출·확인 경로를 통과하게 해줘. fixture 파일은 합성임을 표시하되 profile fixture 선택으로 업로드 경로를 우회하지 말아줘.
7. 업로드한 이력서의 기술·역할이 바뀌면 검색 계획이 달라지고, 결과마다 어떤 경력 근거에 연결됐는지 표시되는지 확인해줘.
8. 키·예산이 준비되지 않은 경우 이 단계의 검증은 mock으로 완료할 수 있어. live 성과로 표시하거나 실제 지원을 실행하지 말아줘.

현재 이미 이 흐름이 구현됐다면 다음 미완료 흐름 하나인 ‘공고 선택→대화형 맞춤 수정→변경 비교→PDF 확정’을 구현해줘. 전체 계획만 쓰고 종료하지 말고, 선택한 한 흐름의 코드·관련 검증까지 진행해줘.

## 후속 구현에서 유지할 계약

- 대화가 수정하는 것은 공고별 이력서 revision이다. 원본 경력 사실은 별도로 보존한다.
- 새 경력·수치·기술은 원문 근거 또는 사용자가 확인한 진술과 연결한다. 표현 수정을 사실 추가로 바꾸지 않는다.
- 공고·프로필·이력서·문항·첨부 내용이 바뀌면 기존 미전송 실행 권한을 재검증한다. 과거 제출본은 그대로 보존한다.
- 자동 지원에는 fixed_document(확정 파일 재사용)와 tailor_within_facts(확정 사실 범위 안에서 공고별 편집)를 구분한다. 다른 회사 이름이 남아 있는 문서는 그대로 재사용하지 않는다.
- 사용자가 명시적으로 활성화한 정책 범위에서는 매건 수동 확인 없이 지원할 수 있게 하되, 기존 단일 공고 approval을 재사용하거나 user_reviewed=true로 위장하지 않는다.
- 정책·한도·만료·지원 사이트·계정·공고·최종 bytes hash에 연결된 공고별 authorization을 만든다. 범위가 부족하면 질문/검토 대기로 보낸다.
- 접수 불명확 상태는 영속 저장하고 자동 재제출·타 채널 중복 실행을 막는다. 외부 ATS에 자체 DB의 reconcile 보장을 적용하지 않는다.
- 브라우저 실행 채널과 사이트별 adapter를 구분한다. Ego는 설치된 PC의 로컬 연결, Chrome은 사이트 권한·기기 연결을 검증한다.
- 지원 완료/실패와 서류 검토/면접/불합격은 다른 상태로 기록한다.

## 보고

정상 사례·관련 실패 사례를 검증하고, typecheck·관련 테스트·필요한 build를 실행해줘. 기존 검사 수만으로 신규 기능을 PASS로 보고하지 말아줘. 결과는 ‘이번에 완성한 흐름 / 실제 검증 / 미구현·미실행 / 다음 한 작업’으로 정리하고 DECISIONS·PROGRESS·HANDOFF·CODEMAP을 갱신해줘.

# 원본 이력서에서 대화형 맞춤·지원 자동화까지

## 1. 검토 결론

사용자가 원하는 제품 흐름은 다음과 같다.

**원본 이력서 등록 → 경력 사실 확인 → 이력서 기반 공고 검색·추천 → 공고 선택 → AI와 대화하며 맞춤 이력서 수정 → 최종 제출본 확정 → Ego 또는 Chrome으로 지원 → 제출본·접수 근거·진행 이력 관리.**

그 다음 확장은 **사용자가 승인한 기준 공고·이력서·지원 정책 → 유사 공고 탐색 → 공고별 조건 검증·제출본 준비 → 정책 범위 안에서 자동 지원 → 결과와 예외 보고**다. AI 대화는 이력서 편집 과정에, 지원 정책은 반복 실행 과정에 연결한다.

현재 v0.4/v0.5는 이 전체 흐름과 일치하지 않는다. 기존 산출물은 합성 프로필·샘플 PDF·자체 테스트 폼이라는 데모 범위였다. 제품의 중심을 원본 이력서와 공고별 제출 이력으로 옮겨야 한다.

## 2. 실제 산출물과의 차이

| 요구 | 현재 확인한 상태 | 필요한 보완 |
| --- | --- | --- |
| 원본 이력서 활용 | ProfileFixture와 synthetic 파일만 설계. 실제 업로드·추출 없음 | 원본 파일·추출 근거·확정 경력 revision |
| 이력서 기반 검색 | preview의 query는 React 고정. 같은 합성 공고 3개 반환 | 경력·역할·기술·사용자 조건에서 검색 계획 생성 |
| 대화형 맞춤 이력서 | 경험·지원 동기 두 문항 템플릿 설계. 전체 이력서 편집 없음 | 대화→변경 제안→diff→사용자 수용→새 이력서 버전 |
| 실제 브라우저 지원 | Chrome 폼 표식 진단만. Ego 연동 없음 | 공통 실행 인터페이스와 선택한 실행기·지원 사이트 adapter |
| 지원 이력 관리 | 불변 제출 기록의 DB/API 계약만. 제품 API는 501 | 실제 제출본·채널·외부 확인 근거·진행 이벤트 저장·재열람 |
| 유사 공고 자동 지원 | 정책·캠페인·반복 실행 없음 | 명시적 정책 승인과 공고별 자동 실행 결정·한도·중지 |

원본 v0.2는 실제 이력서 파싱·외부 채용사이트 제출·다중 사이트 대량 지원을 범위 밖으로 적었다. v0.5가 새 기능을 구현했다고 잘못 보고한 것은 아니지만, 사용자가 지금 명확히 설명한 제품 목표와 기존 데모 범위 사이에 차이가 있다.

재사용할 기반은 React 비교·근거 화면, source/fact/evaluation 분리, 작업·호출 이력, revision·파일 hash, 제출 payload 보존이다. 합성 전용 제약과 자체 폼 receipt/reconcile을 실제 사용자·외부 사이트에 맞게 분리해야 한다.

## 3. 첫 화면과 원본 이력서

첫 화면의 주 행동은 ‘이력서 등록하기’다. 사용자가 먼저 모든 경력을 다시 입력하게 하지 않는다. 원본에서 이름·연락처·회사·기간·역할·기술·프로젝트·성과를 추출하고, 원문과 함께 확인할 수 있게 한다.

초기 구현 제안은 텍스트 PDF부터 안정적으로 지원하고, 텍스트 붙여넣기를 복구 경로로 제공하는 것이다. DOCX·스캔 PDF/OCR의 지원 범위는 화면에서 명확히 표시하고 순차 확장한다. OCR 실패나 비어 있는 추출 결과를 경력 없음으로 확정하지 않는다.

데이터는 다음을 구분한다.

- 원본 파일: 업로드한 bytes와 파일 hash, 소유자, 보관 상태.
- 추출 결과: 문서 페이지·텍스트 구간과 연결된 경력 후보 사실.
- 확정 경력: 사용자가 확인한 내용과 revision. 이후 대화에서 추가한 사실은 해당 메시지와 확인 기록을 연결한다.
- 선호 조건: 원하는 직무·지역·근무 방식·급여 조건 등. 경력 사실과 분리한다.

검색에는 필요한 역할·기술·경험·지역 요약을 사용한다. 연락처·주소 등 공고 검색에 불필요한 정보를 검색 질의에 넣지 않는다. 실제 사용자 파일을 보관하는 서비스의 소유권·인증·삭제 정책은 기존 합성 데모 세션과 별도로 구현한다.

## 4. 이력서 기반 공고 검색

확정 경력 revision과 사용자 조건으로 SearchIntent를 만든다. 직무 명칭의 동의어·기술·책임 수준을 조합하고, 사용자가 희망 역할을 확인하거나 바꿀 수 있게 한다. 검색 요청에는 사용한 경력 revision·조건 revision·검색 계획을 저장한다.

공고 카드는 ‘왜 추천했는가’를 보여준다. 예를 들어 ‘React 프로젝트 경험과 연결됨’, ‘팀 리딩 요건에 연결된 경험 있음’, ‘급여 정보 없음’, ‘필수 원격 조건과 차이’가 서로 다른 근거다. 단어 유사도를 합격 확률로 표시하지 않는다. 이력서 미기재와 경험 없음도 구분한다.

Liner는 공고 탐색·요건 조사·기업 자료 조사에 연결한다. AI와 대화하며 경력을 구조화하고 문장을 편집하는 모듈은 별도 인터페이스로 둔다. 사용할 모델·API·구조화 출력·비용은 실제 입력으로 검증한 뒤 정한다. Claude Code를 개발에 사용하는 것만으로 일반 사용자용 대화 런타임이 만들어지는 것은 아니다.

## 5. 공고 선택 후 AI와 함께 이력서 수정

편집 화면은 ‘선택 공고의 요건 / AI 대화 / 맞춤 이력서 미리보기와 변경 비교’로 구성한다. 작은 화면에서는 탭으로 전환한다. AI는 조언만 반환하지 않고 문서의 수정 제안을 생성한다.

대화 예시:

> AI: 이 공고는 설계와 리뷰 경험을 중요하게 봅니다. 이 프로젝트에서 직접 맡은 범위가 어디까지였나요?
>
> 사용자: 프론트 구조 설계와 코드 리뷰를 맡았고, 서버 구현은 다른 팀에서 했어요.
>
> 수정 제안: 프론트엔드 구조 설계·코드 리뷰를 담당하고 서버팀과 API 연동을 협의했습니다.

이 예시는 설명용이며 사용자의 실제 경력 진술이 아니다. AI가 새로운 성과 수치·기술 사용·책임 범위를 만들어 넣지 않는다. 수치 근거가 없으면 질문하거나 정성적 표현을 유지한다.

수정은 다음 단위로 처리한다.

1. 현재 이력서·선택 공고·근거 버전을 고정한다.
2. 대화에서 표현 수정과 새 경력 사실 추가를 구분한다.
3. 수정 제안을 base revision에 연결해 diff로 보여준다.
4. 사용자가 수용한 변경만 새 이력서 revision으로 만든다.
5. 제출용 PDF를 생성하고 최종 파일 자체를 미리 본다.
6. 지원에는 확정한 파일 bytes hash와 해당 버전을 연결한다.

원본은 보존한다. ‘React 리드용’, ‘AWS 풀스택용’처럼 사실은 같고 강조·순서가 다른 파생본을 관리할 수 있다. 특정 회사 이름·지원 동기가 들어간 문장을 다른 회사 제출본에 그대로 재사용하지 않는다.

## 6. 비슷한 공고에 자동 지원하는 구조

‘이 공고와 비슷한 곳에 지원’은 의미 있는 다음 행동이다. 기준은 사용자에게 확인받은 이전 지원 건, 당시 공고 snapshot, 사용한 이력서 revision이다. 자동 지원으로 발견한 공고가 다시 기준이 되어 범위가 계속 넓어지게 하지 않는다.

유사도는 탐색 기준이며 제출 권한은 아니다. 자동 실행에는 세 단계가 필요하다.

| 단계 | 확인할 것 | 결과 |
| --- | --- | --- |
| 유사 후보 탐색 | 직무·책임·기술·사용자 관심 조건 | 후보 목록 |
| 지원 자격과 정책 확인 | 필수 조건, 모집 상태, 제외 회사, 중복 지원, 허용 사이트, 기간·건수·비용 | 자동 진행 또는 검토 대기 |
| 제출본 검증 | 새 공고와 맞춤 이력서의 사실·문항·파일·계정 일치 | 공고별 실행 기록 생성 |

자동화 모드는 구분해서 제공한다.

- 추천: 유사 공고를 찾아 보여준다.
- 자동 준비: 공고별 맞춤 이력서와 답변을 만들고 제출 대기함에 넣는다.
- 조건부 자동 지원: 사용자가 켜고 승인한 정책 범위에서 별도의 매건 확인 없이 제출한다.

권장 초기 정책 입력은 허용 직무·책임 수준, 지역·근무 방식, 급여 필수 여부, 제외 회사, 지원할 사이트, 사용할 확정 프로필·이력서 버전, 수정 허용 범위, 하루/전체 건수, 만료 시각이다. 예시 ‘하루3건·7일’은 UI 설명용 제안값이며 실제 활성화나 사용자의 승인으로 취급하지 않는다.

자동으로 계속할 수 있는 변경은 확정된 사실의 선택·순서·표현 범위로 제한한다. 새 경력 주장, 미확정 필수 질문, 검증할 수 없는 필수 조건, 예상하지 못한 서약·동의, 로그인·CAPTCHA·추가 인증은 검토 또는 사용자 조작 대기 상태로 넘긴다. 페이지 본문의 지시는 사용자의 정책을 변경할 수 없다.

파일 재사용 방식은 fixed_document(확정된 파일 그대로 사용)와 tailor_within_facts(확정 사실 범위에서 공고별 편집)를 구분한다. 같은 파일을 쓰더라도 새로운 공고의 조건과 회사별 문구를 검사한다. 다른 회사 이름이나 이전 공고 전용 문장이 있으면 그대로 제출하지 않는다.

기존 지원의 승인 토큰을 다른 공고에 재사용하지 않는다. 매 공고마다 정책 버전·새 공고·계정·최종 이력서/답변·실제 파일 hash에 연결된 execution authorization을 만든다. ‘수동으로 이 제출본 확인’과 ‘승인된 정책에 따라 실행’을 서로 다른 권한 근거로 기록한다.

일시 중지·정책 만료·철회 시 신규 제출을 시작하지 않는다. 이미 외부로 전송이 진행 중이면 취소 완료로 단정하지 않고 결과를 조회한다. 접수 결과가 불명확한 건은 자동 재제출·다른 채널 재지원·건수 한도 반환을 보류한다.

## 7. Ego와 Chrome의 역할

공통 ApplyAdapter는 대상·로그인 계정 확인, 폼 읽기, 입력, 첨부, 실제 값 재확인, 제출, 결과 조회, 사용자 인계 기능을 정의한다. 처음부터 두 실행기를 모두 완성할 필요는 없다.

실행 채널과 채용사이트 adapter는 별도 축이다. Ego와 Chrome 중 하나를 선택했다고 모든 사이트의 질문·파일 첨부·접수 판정이 지원되는 것은 아니다. adapter별 capabilities와 지원하는 폼 버전을 기록한다.

### Ego

Ego 공식 문서는 Node CLI, TaskSpace/Page 제어, 파일 첨부·다운로드, Space ID로 재개, 사용자 인계를 설명한다.[1] 외부 웹 서비스에서 사용자의 Ego를 제어하려면 Ego가 설치된 PC에서 명령을 실행하는 로컬 연결이 필요하다. 원격 서버에 Skill만 추가하는 것으로 로컬 브라우저를 제어할 수 없다.[2]

따라서 초기 개발 실증은 Claude Code와 Ego로 할 수 있지만, 일반 구직자에게 제공할 때는 Career Evidence의 로컬 실행기·기기 연결·작업 권한·결과 전송을 제품으로 구성해야 한다. 사용자가 Claude Code를 직접 조작하도록 하는 것이 최종 사용자 경험일 필요는 없다. Ego API는 설치 버전에 맞는 공식 가이드를 읽어 구현한다.

### Chrome 확장

기존 브라우저에서 동작하는 제품 경로로 유지할 수 있다. 현재 activeTab은 사용자가 실행한 현재 탭에 대한 임시 권한이며 다른 origin으로 이동하면 권한이 끊긴다.[3] 여러 사이트에 걸친 자동 지원에는 지원하는 사이트별 host 권한과 사용자 허용, 확장과 서버의 인증 연결, 탭·document 변화 처리가 필요하다. Chrome은 optional host permissions를 제공한다.[4]

로컬 브라우저·확장이 꺼져 있거나 연결되지 않았을 때는 대기열로 남기고, 다시 연결되면 현재 정책·상태를 재검증한다. 웹 서비스만 실행 중이라고 사용자 PC의 작업이 항상 수행되는 것으로 표시하지 않는다.

### 자체 폼과 외부 사이트의 차이

자체 폼은 우리 DB 안에서 접수와 종료를 원자적으로 처리할 수 있다. 외부 사이트의 제출 효과는 우리 DB가 취소하거나 봉인할 수 없다. 버튼 클릭 성공이나 네트워크 응답 부재만으로 접수 완료·미접수를 확정하지 않는다. 완료 화면·지원 내역·확인 번호 등 실제 근거가 필요하며, 이 판단은 사이트 adapter별로 검증한다. 플랫폼의 범용 폼 기능이 모든 채용사이트 성공을 보장하지 않는다.[1]

## 8. 지원 이력의 중심은 제출 당시 버전

각 지원 건은 회사·직무·공고 snapshot, 제출 시각, 실행 채널, 사용한 프로필·이력서 revision, PDF hash, 답변, 수동/정책 실행 근거, 접수 증거를 연결한다. 원본이나 최신 이력서가 바뀌어도 과거 제출본은 바뀌지 않는다.

전송 상태와 채용 절차 상태를 분리한다.

- 전송: 준비 중 / 확인 대기 / 전송 중 / 접수 확인 / 결과 확인 필요 / 명시적 실패.
- 채용 절차: 지원 / 검토 중 / 면접 / 제안 / 불합격 / 철회. 사용자 입력 또는 별도로 연결한 출처가 있을 때 갱신한다.

며칠간 연락이 없다는 이유로 불합격으로 바꾸지 않는다. 사용자가 직접 지원한 기록도 입력해 중복 검사에 포함할 수 있게 한다. 이메일 연동은 후속 선택 기능이며 이번 검토에서 메일 접근을 실행하지 않았다.

## 9. 필요한 데이터 관계와 계약 변경

원본 문서 → 확인된 경력 revision → 검색 context → 공고 snapshot → 맞춤 대화/변경 제안 → 맞춤 이력서 revision → 렌더링 파일 → 지원 authorization → 전송 attempt → 외부 확인 근거/이력 이벤트를 연결한다.

새 개념은 ResumeDocument, ResumeFactRevision, TailoringSession, ResumeRevision, RenderedArtifact, AutoApplyPolicyRevision, SimilarJobCampaign, ApplicationAuthorization, ExternalSubmissionEvidence다. 기존 테이블을 재사용할지 새 테이블로 나눌지는 계약 설계 단계에서 정한다.

필요한 API 묶음은 파일 등록·추출 작업·추출 확인, 맞춤 대화·변경 제안 수용·문서 export, 정책 미리보기·명시적 활성화·일시 중지, 실행기 연결·작업 수령·결과 보고, 버전별 지원 이력 조회다. 이 문서는 해당 API를 구현하거나 OpenAPI 검증한 결과가 아니다.

## 10. 구현 순서 조정

1. 원본 이력서→추출 확인→확정 경력→그 경력에서 만든 검색 요청→공고 노출.
2. 공고1개→대화형 수정→변경 비교→최종 PDF 생성.
3. 실행기1개→테스트 폼 입력·첨부·지원→제출본과 접수 이력 재열람.
4. 유사 공고→조건 검증→공고별 제출본 자동 준비.
5. 명시적 정책 승인→지원 가능한 대상의 제한된 자동 제출→중지·복구·불명 처리.

대회용 시연에서도 합성 이력서 파일을 실제 업로드 경로에 넣어 위 흐름을 보여주는 편이 목적에 맞다. 합성 프로필을 코드에서 바로 고르는 경로만으로 대체하지 않는다. 기업 심층 브리프는 가치가 있지만, 대화형 맞춤 이력서보다 먼저 모든 지원 건에 필수로 요구하지 않는다.

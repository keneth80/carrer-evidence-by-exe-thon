# 개발자 담당 작업 시작 — 팀 패키지 v0.8

현재 사용자 요청과 합의된 담당 범위에서 Career Evidence를 구현해줘. 제품·데이터 계약은 v0.7, 팀 작업 기준은 `docs/team/TEAM_WORKPLAN.md`와 `docs/team/tasks.json`이야. 개발 도구는 Claude Code야.

## 시작

1. 루트 CLAUDE.md, DECISIONS.md, docs/state/PROGRESS.md, docs/state/HANDOFF.md, docs/CODEMAP.md를 읽어줘.
2. 팀 업무표의 확정 담당이나 이번 사용자 요청이 있으면 그 범위를 우선해줘. tasks.json은 초기 계획이고 XLSX의 변경이 자동 반영된다고 가정하지 말아줘.
3. 현재 경로·Git 상태·사용자 변경·작업 중인 파일을 확인하고 기존 구현을 활용해줘.
4. 분담안이 아직 확정되지 않았으면 이 요청으로 맡긴 로컬 범위의 유용한 작업부터 진행하고, 협업자에게 맡겼다고 임의로 확정하지 말아줘.

## 우선 구현

첫 공동 목표는 이력서 등록 → 추출 확인 → 확정 경력 → SearchIntent → 영속 검색 → 공고 노출이야. 개발 분담안에서는 T07·T09의 웹 흐름을 맡고, 협업자의 T06·T08 API와 연결해줘. API가 아직 준비되지 않았으면 v0.7 계약 예제로 화면·상태·입력 검증을 먼저 구현하고 실제 연결까지 무엇이 남았는지 기록해줘.

개발+검수안에서는 개발자가 T05~T09의 기술 구현을 단계별로 연결하고, 협업자에게 T04 기대값과 T10 인수 결과를 받는 구조야. 이번 요청에서 선택한 한 흐름의 코드와 관련 검증까지 마쳐줘. 전체 계획만 남기고 끝내지 말아줘.

후속 담당은 대화 편집·diff·PDF·Chrome·지원 이력 화면이야. 대화 편집과 PDF는 전용 모듈로 작성하고, 공용 router·worker 연결이 협업자 담당이면 입력/출력/오류 예제를 인계해줘. 새 파일 경로는 생성 후 CODEMAP에 반영해줘.

## 협업과 검증

- 같은 파일을 다른 개발 세션이 수정 중이면 별도 작업 브랜치나 모듈에서 작업하고 통합 시 변경을 비교해줘. 사용자 변경을 덮어쓰지 말아줘.
- 공통 계약이 바뀌면 Schema·API·타입·예제·UI에 미치는 영향을 함께 정리해줘. 합의된 로컬 범위의 수정·검증은 계속 진행해줘.
- 합성 이력서도 실제 업로드 경로를 통과시켜 확인해줘. 고정 query나 fixture 선택으로 제품 흐름을 완료 처리하지 말아줘.
- mock/live, 실제 생성 파일/화면 텍스트, 자체 폼/외부 사이트 검증을 구분해줘.
- 자동 지원은 활성 정책 안에서 매건 확인 없이 실행할 수 있게 하되, 공고별 권한과 접수 불명 중복 차단을 유지해줘.

## 인계

작업 ID, 완료한 사용자 동작, 변경 파일, 검사 결과, 상대에게 넘길 호출 예제, 남은 연결, 다음 한 작업을 한국어로 보고해줘. 실제 완료 근거에 맞춰 상태를 갱신하고 미구현 기능을 완료로 표시하지 말아줘. 이 개발 작업만으로 외부 메시지를 보내거나 실제 기업에 지원하지 말아줘.

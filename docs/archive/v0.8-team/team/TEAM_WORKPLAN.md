# Career Evidence 2인 팀 업무 분장·실행 계획 v0.8

작성일: **2026-11-16 · Asia/Seoul**. 제품·API 기준은 통합 명세 v0.7이다. 이 문서는 개발자와 팀원(이하 ‘협업자’)이 역할을 정하고 작업을 이어가기 위한 **협의안**이다. 협업자의 개발 분야와 두 사람의 가용시간은 아직 확인되지 않았다. 업무표의 확정 담당과 확정 검토자는 비워 두고 모든 작업은 미착수로 시작한다.

## 1. 함께 완성할 목표

보유 이력서 등록 → 내용 확인 → 이력서 기반 공고 검색 → 공고 선택 → AI와 대화하며 맞춤 수정 → 실제 제출 PDF → 브라우저 지원 → 제출본·접수 이력 → 유사 공고 자동 준비·조건부 자동 지원을 연결한다.

첫 완료 목표는 **이력서 파일이 실제 등록·추출·확인 경로를 통과하고, 그 경력 때문에 검색 계획과 추천 이유가 달라지는 것**이다. 현재 패키지는 기초 코드와 설계·계약을 제공한다. 업로드·대화·실제 지원·자동 지원이 이미 완성됐다는 전제로 일을 배정하지 않는다.

제품 범위와 시연 범위를 구분한다. 정책에 따른 유사 공고 자동 지원은 제품에 포함한다. 시연에서는 구현·검증한 범위를 보여주며, 첫 브라우저 경로는 Chrome과 자체 테스트 폼으로 잡는다. Ego와 실제 사이트는 같은 실행 계약의 후속 연결이다.

## 2. 먼저 선택할 두 가지 분담안

### A. 개발 분담안

협업자가 API·DB·worker 개발을 맡을 수 있고 실제 가용시간이 확보될 때 선택한다.

| 담당 | 주 책임 | 상대에게 넘길 결과 |
| --- | --- | --- |
| 개발자 | 제품·웹 화면, 대화형 문서 편집 모듈, PDF 출력, Chrome 실행기, 최종 통합 | 화면 동작·편집/렌더 모듈 계약·브라우저 결과·재현 방법 |
| 협업자 | 인증·소유권·DB, 이력서 추출 API, Liner 검색·worker, 지원 권한·이력 API, 핵심 검수 | 성공/실패/처리 중 API 예제·영속 상태·접수 근거·검증 결과 |
| 공동 | 공통 계약·경력 사실 기준·정책 범위·단계별 완주 검수 | 합의한 결정과 현재 구현 범위 |

대화·PDF는 개발자가 전용 모듈을 만들고, 협업자가 공용 API router·파일 저장·worker 연결을 맡는 구조를 기본안으로 한다. 협업자에게 모든 서버 작업을 한꺼번에 넘기지 않고 단계 1에 필요한 경로부터 연결한다. 작업 건수만으로 부하가 균등하다고 판단하지 않는다.

### B. 개발+검수안

협업자의 강점이 기획·자료·검수·발표이거나 개발 시간이 적을 때 선택한다.

| 담당 | 주 책임 | 책임 있는 산출물 |
| --- | --- | --- |
| 개발자 | 기술 구현·테스트 도구·문제 수정·통합 | 실행 코드와 재현 가능한 검증 |
| 협업자 | 공고·경력 근거 정답표, 사용자 동선·문장·PDF 검수, 단계 인수, 데모·제출 관리 | 기대 결과·실제 결과·판정·근거를 갖춘 검수표와 최종 발표 자료 |
| 공동 | 우선순위·범위·최종 리허설 | 공개할 기능과 남은 기능의 정확한 구분 |

협업자는 단순 보조가 아니라 **사용자 관점의 완료 판단과 데모 품질을 책임지는 역할**이다. 이 안에서는 개발 병목이 개발자에게 집중되므로 A안과 같은 속도를 약속하지 않는다. 실제 가용시간을 확인해 목표일과 시연 범위를 다시 정한다.

### 담당 확정 방법

동봉된 업무표에는 두 안의 제안 담당, 확정 담당, 확정 검토자, 상태, 목표일, 선행 작업, 완료 기준이 분리되어 있다. 선택한 안을 참고해 **각 작업의 실행 책임자 한 명과 검토자 한 명**을 정한다. ‘공동’은 역할 제안이며, 확정 담당에는 실제 진행 책임자 한 명을 적고 상대를 검토자로 둔다. 기술 작업의 검토자가 개발자가 아니면 개발 담당이 재현 도구와 결과를 제공하고, 검토자는 사용자 동작과 기대 결과를 확인한다.

업무표는 협의·진행 관리를 위한 편집본이고 `tasks.json`은 초기 작업 기준이다. 둘이 자동 동기화되는 구조는 아니다. 담당·일정을 바꾼 뒤 관련 결정과 현재 작업은 `DECISIONS.md`, `docs/state/HANDOFF.md`에 반영한다. 실제 실행 결과를 확인하기 전에는 완료로 바꾸지 않는다.

## 4. 서로 충돌하지 않게 나눌 코드 경계

아래는 A안의 제안이다. B안에서는 기술 파일 책임을 개발자에게 모으고 협업자는 검수·자료 파일과 결과 판정을 담당한다. 경로는 현재 존재하는 영역이며, 새 모듈 파일명은 구현할 때 CODEMAP에 등록한다.

| 영역 | 제안 작성 책임 | 연결·검토 방식 |
| --- | --- | --- |
| `apps/web/src/`, `apps/extension/` | 개발자 | 협업자가 정상·실패 동선과 실제 결과 검수 |
| 대화 편집·PDF 전용 모듈(신규 경로) | 개발자 | 입력·출력·오류 타입을 먼저 공유, 협업자가 router/worker에 연결 |
| `apps/api/src/server.ts`와 공용 router | 협업자 | 각 기능 모듈을 연결. 개발자가 통합 확인 |
| `packages/db/src/`, 원본 저장·추출·인증 서비스 | 협업자 | 변경 migration·소유권·실패 복구 결과 공유 |
| `apps/worker/src/`, `packages/liner/src/` | 협업자 | task 상태·mock/live·예산·재시작 결과 공유 |
| `contracts/v0.7/`, 공통 공개 타입 | 협업자 | 요청/응답·DB·예제·화면 영향이 있는 변경을 함께 검토 |
| `package.json`·lockfile·공통 설정·루트 지침 | 개발자 | 필요한 변경을 작게 묶고 두 작업의 실행 호환성 확인 |
| 검수 기준·합성 추가 사례·데모 자료 | 협업자 | 기대값은 구현을 그대로 베끼지 않고 원문·사용자 목표와 대조 |
| `DECISIONS.md`·CODEMAP·상태 파일 | 통합 책임 개발자 | 협업자는 작업별 인계 결과를 전달하고 병합 시 반영 |

작업 ID별 분리된 브랜치/작업 폴더를 사용하고 같은 파일을 두 Claude Code 세션이 동시에 덮어쓰지 않게 한다. 공통 계약 변경이 필요하면 영향 범위와 수정안을 함께 남긴다. 합의된 범위 안의 로컬 수정·검증은 이어가며, 매번 형식적인 허락을 다시 받는 절차로 만들지 않는다. 비밀키는 각자의 허용된 환경 설정으로 관리하고 메시지·저장소·영상에 넣지 않는다.

## 5. 연결 지점마다 주고받을 것

| 연결 | 먼저 제공할 것 | 함께 확인할 것 |
| --- | --- | --- |
| 이력서 화면 ↔ 등록·확정 API | `ResumeDocument`, `ExtractionDraft`, `ResumeFactRevision`의 성공·실패·처리 중 예제 | 파일 hash·원문 위치·확인 전/후·소유 범위 |
| 검색 화면 ↔ 작업·Liner | `SearchIntent`, `SearchRun`, `JobSnapshot`, task 상태 | 이력서 차이·출처·미확인 조건·재시작 조회 |
| 대화/PDF 모듈 ↔ API·저장 | `EditProposal`, `ResumeRevision`, `RenderedArtifact` | base revision 충돌·사실 근거·실제 PDF bytes |
| Chrome ↔ 지원 서버 | `ApplicationRevision`, `ApplicationAuthorization`, `SubmissionAttempt` | 공고·파일·답변·계정·문항 결속·접수 증거 |
| 자동화 화면/실행기 ↔ 정책·worker | 정책 revision·고정 seed·공고별 권한·한도·중지 | 매건 확인 없는 정책 실행·예외 대기·중복 차단 |

각 연결의 인계에는 **입력 예제, 정상 결과, 대표 실패, 처리 중 상태, 호출/재현 방법, 남은 제약**을 넣는다. 계약 예제만으로 각자 먼저 개발할 수 있지만 실제 연동이 없으면 통합 완료로 표시하지 않는다.

자동 제출이 미완료여도 사용자 요구에서 삭제하지 않는다. 개발 상태와 후속 작업으로 유지한다. 실사이트 여러 곳·Ego 동시 구현·DOCX/OCR·이메일 연동은 핵심 완주 뒤 확장한다. 실제 Liner 활용을 요구하는 제출 조건을 mock 표시만으로 충족했다고 주장하지 않는다. 재생한 실제 수집 결과는 수집 시각과 재생 여부를 표시한다.

우선 관리할 통합 의존 경로는 **기반(T03·T05) → 등록·검색(T06·T08·T09·T10) → 대화·PDF(T11~T14) → 지원·이력(T15~T18) → 릴리스·제출(T25~T28)**이다. 실제 소요시간이 없으므로 기간을 계산한 확정 임계 경로는 아니다. T07 같은 화면은 예제 응답으로 병렬 착수한다. T19~T24 자동화는 앞선 공고·문서·지원 기록을 재사용한다. 의존성은 완료 판정 조건이며 기다리는 동안 독립된 검수·화면 작업을 진행할 수 있다.

**11/22~23에 모인 자동화 작업은 특히 가용시간을 먼저 확인해야 한다.** 첫 브라우저 완주 뒤 하루 이틀 만에 모든 자동화가 완료된다고 약속하지 않는다. 계약 예제·정책 화면·검수 사례는 앞서 준비할 수 있지만, 실제 제출 검증은 지원·권한 경로가 연결된 뒤 진행한다. T01에서 한 사람이 감당할 수 있는 작업과 실제 시간을 확인한 다음 목표일을 다시 잡는다.

## 8. 작업을 완료로 바꾸는 기준

- 문서나 함수가 생겼다는 이유만으로 완료 처리하지 않는다. 사용자 행동이 실제로 이어지는지 확인한다.
- 코드 담당은 변경 파일·입출력·실행한 검사·관찰 결과·미실행 범위를 남긴다.
- 검수 담당은 기대 결과와 실제 결과, 수용/수정 필요, 근거를 남긴다. 실행하지 못한 검사는 NOT_RUN이다.
- 원본 경력 과장, 다른 공고 권한 재사용, 접수 불명 자동 재제출, 제출본 덮어쓰기는 해결 전 해당 흐름을 완료 처리하지 않는다.
- 통합 책임자는 변경을 현재 코드와 합치고 관련 검증을 확인한 후 `PROGRESS.md`, `HANDOFF.md`, 필요한 결정·코드맵을 갱신한다.
- 전체 제품의 모든 기능을 매 작업마다 다시 검사하지 않는다. 바뀐 경계와 남은 구체적 위험을 확인하고 다음 작업으로 이동한다.

## 9. 매일 공유할 짧은 인계

아래는 작성 틀이며 실제 완료 보고가 아니다.

```text
작업 ID / 담당:
완료한 사용자 동작:
변경 파일·커밋 또는 검토 자료:
실행한 검증 / 미실행:
상대와 연결할 입력·출력·오류:
막힌 점과 필요한 결정:
다음 한 작업:
```

화면 녹화·JSON 예제·검증 로그에는 합성 자료를 사용한다. 외부 메시지 전송, 실제 기업 지원, 공개 배포, 대회 제출은 이 문서를 작성했다는 사실로 실행된 것이 아니다. 각 작업을 수행한 사람이 범위와 실제 결과를 확인해 기록한다.

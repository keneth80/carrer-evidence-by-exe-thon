# Career Evidence 통합 제품 명세 v0.7

기준일: 2026.11.16 · 문서 상태: 현재 제품·개발 기준 · 구현 상태: `state/PROGRESS.md` 참조

## 1. 제품 목표와 문서 적용 순서

Career Evidence는 **사용자가 가진 이력서로 공고를 찾고, 선택한 공고에 맞춰 AI와 대화하며 이력서를 수정한 뒤, 브라우저 지원과 지원 이력 관리까지 이어주는 서비스**다. 사용자가 정한 범위에서는 유사 공고의 지원 준비와 제출도 자동화한다.

이번 통합본으로 처음 시작하면 이전 패키지를 따로 적용할 필요가 없다. 현재 사용자 흐름은 이 문서와 `UI_UX.md`, 구현 순서는 `IMPLEMENTATION_PLAN.md`, 데이터·HTTP 형식은 `../contracts/v0.7/`, 기술 구조는 `ARCHITECTURE.md`를 따른다. `archive/`, `reference/`, `contracts/v0.4/`는 변경 배경과 기존 코드 회귀 검증을 위한 자료다. 과거의 합성 프로필 전용·실제 이력서 제외 규칙을 현재 제품 범위로 가져오지 않는다.

통합 명세와 계약이 존재한다고 해당 기능이 실행 코드에 구현된 것은 아니다. 포함된 코드의 출발점은 기존 foundation이다. 원본 업로드, 대화 편집, 제품 worker, 브라우저 제출, 자동 지원은 단계별 구현·검증 대상이다.

현재 `/api/v1/*`는 501을 반환하고 DB 초기화는 v0.4 기준이다. v0.7의 `ce7_*` 추가 구조를 사용하려면 명시적 migration runner와 해당 handler를 함께 구현해야 한다. 계약 파일을 추가한 것만으로 기존 DB가 전환되지는 않는다.

## 2. 대상 사용자와 해결할 일

대상은 이미 이력서나 경력 자료를 갖고 있지만, 자신에게 맞는 공고 탐색과 공고별 서류 수정·반복 입력에 시간을 쓰는 구직자다. 특정 기술 직군에만 제한하지 않되 초기 합성 사례는 소프트웨어 직무로 집중한다.

사용자가 원하는 일은 다음과 같다.

- 내 경력과 희망 조건에 맞는 공고를 먼저 보여준다.
- 왜 추천했는지, 어떤 요건이 아직 확인되지 않았는지 알려준다.
- 대화에서 추가한 설명이 실제 이력서 문장과 구성에 반영된다.
- 확인한 제출본을 정확한 공고에 첨부하고 접수 결과를 남긴다.
- 이미 잘 준비한 지원을 기준으로 비슷한 공고의 반복 작업을 줄인다.
- 어느 회사에 어떤 내용을 제출했는지 나중에 다시 확인한다.

제품의 성과는 지원 횟수만으로 평가하지 않는다. 준비 완료까지 걸린 시간, 사용자가 수용한 수정의 비율, 접수 증거가 있는 지원 비율, 중복·잘못된 서류 제출, 확인이 필요한 사유 등을 함께 본다. 숫자 목표는 실제 사용 데이터를 얻은 뒤 정하며 합격률 향상을 보장하지 않는다.

## 3. 전체 사용자 흐름

1. **이력서 등록:** 기존 파일을 올리거나 텍스트를 붙여 넣는다.
2. **내용 확인:** 추출된 경력과 원문을 비교해 수정·확정한다.
3. **공고 추천:** 확정 경력과 희망 조건에서 검색 계획을 만들고 공고를 보여준다.
4. **공고 선택:** 관심 공고의 요구사항과 경력 근거를 확인한다.
5. **대화형 수정:** AI와 대화하면서 변경 제안을 받고 수용한다.
6. **제출본 확정:** 실제 PDF와 추가 답변을 확인하고 버전을 고정한다.
7. **브라우저 지원:** 선택한 실행기가 폼 입력·첨부·확인·제출을 수행한다.
8. **이력 관리:** 당시 공고·이력서·답변·접수 결과를 저장한다.
9. **유사 공고:** 선택한 지원 건을 고정 기준으로 탐색한다.
10. **설정에 따른 반복:** 추천, 자동 준비, 조건부 자동 지원 중 선택한 모드로 처리한다.

기업 심층 조사는 필요한 공고에서 선택적으로 요청할 수 있다. 모든 지원 전에 기업 브리프를 반드시 완성해야 하는 흐름으로 만들지 않는다.

## 4. 원본 이력서와 경력 확인

### 4.1 입력 범위

첫 구현은 텍스트를 추출할 수 있는 PDF와 텍스트 붙여넣기를 지원한다. 2026-11-19부터 Word(.docx)의 본문·표 텍스트도 지원한다(DECISIONS S1-12). 옛 .doc와 스캔 PDF의 OCR은 후속 단계다. 실제 지원 형식과 파일 크기·페이지 한도를 업로드 화면에 표시하고 서버가 같은 제한을 검증한다. 스캔 문서를 빈 경력으로 처리하지 않는다.

원본 파일은 `ResumeDocument`에 연결한다. 파일의 실제 bytes hash, 소유 범위, 업로드 시각, 추출 상태를 저장한다. 추출 후보는 원문 페이지·텍스트 구간 또는 붙여넣기 구간을 참조한다. 원본에 없는 내용은 원문에서 추출했다고 표시하지 않는다.

### 4.2 사용자 확인

추출된 회사, 기간, 역할, 기술, 프로젝트, 담당 범위, 성과를 확인할 수 있게 한다. 잘못 추출된 내용을 수정하면 수정의 출처를 사용자 확인으로 남긴다. 확인한 내용은 불변 `ResumeFactRevision`으로 저장한다.

연락처·주소와 경력 사실은 용도에 맞게 구분한다. 공고 검색에는 직무·기술·책임 수준과 필요한 지역 조건을 전달하고 전화번호·이메일·상세 주소를 검색어에 넣지 않는다. 사용자 화면에는 검색에 사용할 요약과 조건을 확인하는 경로를 제공한다.

희망 직무·지역·연봉·근무 방식은 경력 사실과 별개다. ‘React 경험이 있음’과 ‘React 리드로 일하고 싶음’은 다른 정보다. 미확인 경력, 경험이 없다는 사용자 진술, 공고에 기재되지 않은 조건도 구분한다.

### 4.3 소유권과 보관

파일, 추출 결과, 대화, 생성 문서, 지원 이력의 접근은 인증된 사용자와 workspace 소유권으로 검증한다. 브라우저가 보내는 사용자 ID만으로 권한을 부여하지 않는다. 실제 사용자 서비스에는 인증·보관·삭제 기능이 필요하며 합성 데모 세션을 그대로 운영 인증으로 사용하지 않는다.

원본 삭제, 특정 제출 이력 삭제, 계정 전체 삭제는 영향 범위가 다르므로 사용자에게 범위를 표시한다. 삭제한 자료를 새 검색이나 자동 지원의 입력으로 재사용하지 않는다. 제출 당시 파일을 보관하는 정책과 전체 삭제 동작은 서비스 출시 전에 일관되게 구현한다.

## 5. 이력서 기반 공고 검색

확정한 경력과 희망 조건에서 `SearchIntent`를 만들고, 실행 시 `SearchRun`으로 저장한다. 직무 명칭·동의어·기술·책임 수준을 검색 계획에 반영한다. 기본 query를 `React`로 고정하거나 모든 이력서에 같은 후보를 반환하는 preview를 제품 검색으로 사용하지 않는다.

공고는 `JobSnapshot`으로 저장하며 원문 주소·확인 시각·내용과 연결한다. 검색 및 요구사항 조사에는 Liner 어댑터를 사용한다. 개발용 mock은 외부 호출 없이 결정적으로 재현할 수 있게 하고, 화면과 기록에서 합성 결과임을 표시한다. 실제 Liner 기능·모델·비용은 현재 공식 계약과 실측으로 확인한다.

공고 카드에는 다음을 표시한다.

| 정보 | 표시 원칙 |
| --- | --- |
| 회사·직무·지역·고용 형태 | 확인한 공고 정보와 출처를 연결 |
| 추천 이유 | 어떤 확정 경력과 어떤 공고 요구가 연결됐는지 설명 |
| 확인할 조건 | 미기재·미확인·추가 질문 필요를 구분 |
| 조건 차이 | 사용자의 필수 조건과 확인된 공고 조건의 차이를 표시 |
| 지원 상태 | 이미 지원했거나 접수 결과가 불명확하면 표시 |
| 다음 행동 | 공고 보기, 관심 저장, 이 공고에 맞춰 수정 |

문자열 유사도를 합격 확률로 보여주지 않는다. 필수 조건이 미확인인 공고를 자동 지원 대상으로 바로 확정하지 않는다. 희망 조건만 바꿨을 때 저장된 근거로 재평가할 수 있으면 먼저 재평가하며, 새 탐색 요청은 별도로 구분한다.

## 6. 대화형 맞춤 이력서

### 6.1 편집 단위

선택한 `JobSnapshot`과 `ResumeFactRevision`으로 `TailoringSession`을 시작한다. 대화 메시지 `TailoringMessage`와 변경 제안 `EditProposal`을 구분해 저장한다. 대화 답변은 실제 문서 변경 제안을 포함할 수 있어야 한다.

이 대화형 수동 편집에서는 사용자가 수용한 변경으로 새 `ResumeRevision`을 만든다. 제안은 적용할 base revision을 명시한다. 다른 탭에서 문서를 바꿨거나 사용자가 기반 경력을 바꾸면 오래된 제안을 자동으로 덮어쓰지 않는다. 8절의 정책 자동 편집은 미리 허용된 사실·수정 범위 안에서 별도 수동 수용 없이 새 revision을 만들 수 있으며, 적용 근거를 사용자 직접 수용과 구분해 기록한다.

### 6.2 대화의 역할

AI는 공고의 중요한 요구를 찾아 사용자에게 맡은 범위, 협업 방식, 결과를 구체적으로 질문한다. 예시는 합성이다.

> AI: “이 공고는 설계와 코드 리뷰 경험을 중요하게 보고 있어요. 해당 프로젝트에서 직접 맡은 범위가 어디까지였나요?”
>
> 사용자: “프론트 구조와 리뷰 기준을 정했고, 서버는 다른 팀이 만들었어요.”
>
> 변경 제안: “프론트엔드 구조와 코드 리뷰 기준을 정비했습니다.”

없는 기술 사용, 자격, 성과 수치, 직책, 책임 범위를 만들어 넣지 않는다. 새 경력 사실이 대화에 나오면 사용자 확인 기록과 연결한다. AI가 작성한 문장을 다시 독립적인 경력 사실의 증거로 삼지 않는다.

### 6.3 사용자 제어

- 제안별 수용·거절·수정과 전체 변경 비교를 제공한다.
- 근거가 부족한 문장은 ‘확인 필요’로 표시하고 제출 확정 전에 해결한다.
- 원본은 보존하고 공고별 파생 문서를 만든다.
- 되돌리기는 과거 이력을 지우지 않고 새 revision으로 기록한다.
- 대화의 전송 중단·실패 시 수용하지 않은 변경을 임의로 확정하지 않는다.

### 6.4 최종 파일

확정한 revision에서 `RenderedArtifact`를 생성한다. 최종 미리보기는 제출할 실제 PDF를 사용한다. 한글 글꼴, 줄바꿈, 페이지 잘림, 링크, 읽기 순서를 확인하고 실제 파일 hash를 저장한다. 생성 실패한 경우 화면 텍스트가 있다는 이유로 제출 가능 상태를 표시하지 않는다.

## 7. 브라우저 지원과 이력

첫 실행기는 기존 골격을 활용한 Chrome 확장으로 정하고 자체 테스트 폼에서 완주한다. Ego는 같은 ApplyAdapter 계약의 후속 실행 채널이다. 첫 실제 채용사이트는 별도 검증으로 정하며, 그 선택 전에도 전체 로컬 흐름을 구현할 수 있다.

브라우저 종류와 지원 사이트는 별도 지원 범위다. `chrome + 자체 폼`이 검증됐다고 모든 ATS가 지원되는 것으로 표시하지 않는다. 화면에는 실행기 연결 여부와 현재 사이트의 지원 범위를 보여준다. 상세 연결은 `BROWSER_ADAPTERS.md`를 따른다.

각 `Application`은 공고, 확정 경력, 제출 이력서·파일, 추가 답변을 고정한다. 수동 확인 또는 자동 지원 정책에 따른 `ApplicationAuthorization`을 만든 뒤 `SubmissionAttempt`를 실행한다. 파일·공고·계정·질문·답변이 바뀌면 미사용 실행 권한을 재검증한다. 제출한 과거 기록은 최신 문서로 덮어쓰지 않는다.

`SubmissionEvidence`는 완료 화면, 확인 번호, 사이트의 지원 내역 등 접수 여부를 확인하는 근거를 기록한다. 클릭 반환만으로 지원 완료를 만들지 않는다. 접수 결과가 불명확하면 확인 대기로 보존하고 자동 재제출이나 다른 채널의 중복 제출을 막는다.

지원 이력에는 제출 상태와 채용 진행 상태를 나누어 표시한다.

| 축 | 사용자 표시 예시 | 갱신 근거 |
| --- | --- | --- |
| 제출 상태 | 준비 중, 사용자 확인 필요, 브라우저 연결 대기, 전송 중, 접수 확인, 접수 확인 필요, 제출 실패 | 실행기·사이트의 관찰 결과 |
| 채용 진행 | 지원, 서류 검토, 면접, 제안, 불합격, 철회 | 사용자 입력 또는 별도로 연결한 확인 가능한 출처 |

응답이 없다는 이유로 채용 불합격을 추정하지 않는다. 직접 지원한 기록도 사용자 입력으로 추가해 중복 검사에 포함한다. 이메일 자동 동기화는 후속 선택 기능이다.

## 8. 유사 공고와 조건부 자동 지원

### 8.1 고정한 기준

사용자가 선택한 지원 건, 당시 공고 snapshot, 경력·이력서 revision을 `SimilarJobCampaign`의 기준으로 고정한다. 자동 지원으로 발견한 공고에서 새 기준이 연쇄적으로 파생되게 하지 않는다. 기준이나 지원 정책 변경은 새 버전과 명시적인 사용자 동작으로 처리한다.

### 8.2 세 가지 모드

| 모드 | 수행 | 제출 권한 |
| --- | --- | --- |
| 추천 | 유사 공고와 추천 근거 수집 | 없음 |
| 자동 준비 | 공고별 적합 조건 확인, 이력서·답변 준비, 검토 목록 생성 | 없음 |
| 조건부 자동 지원 | 정책 안의 공고에 준비·검증·제출 | 사용자 활성화 정책에서 공고별 권한 생성 |

조건부 자동 지원에서는 활성 정책 범위를 충족한 건마다 수동 확인을 반복하지 않는다. 준비 모드에서 제출 모드로의 변경은 사용자가 범위를 확인하고 활성화하는 행동을 요구한다.

### 8.3 정책 내용

`AutoApplyPolicyRevision`은 다음을 고정한다. 구체 필드·enum은 v0.7 계약을 따른다.

- 사용할 경력 revision, 기준 이력서, 지원 계정과 허용 실행 범위
- 직무·책임 수준·고용 형태·지역·근무 방식과 필수 조건
- 제외 회사, 허용 사이트, 중복 판단 기준
- 일일·전체 건수, 비용 한도, 종료 시각, 시간대
- 파일 재사용 또는 확정 사실 범위에서의 문서 수정
- 자동 답변이 가능한 항목과 사용자 확인이 필요한 항목

예를 들어 ‘하루 3건, 7일’은 설정 화면 설명용이다. 초기값을 넣는 것만으로 제출 동의를 얻은 것으로 보지 않는다. 한도 집계는 정책 시간대를 사용하며 일시중지·재개나 작업 재시작으로 초기화하지 않는다.

문서 방식은 `fixed_document`와 `tailor_within_facts`로 구분한다. 앞의 방식은 확정한 파일을 그대로 쓰되 다른 회사 이름과 해당 공고의 제출 조건을 점검한다. 뒤의 방식은 확인된 사실의 선택·배치·표현만 허용하며 새 경험이나 수치를 생성하지 않는다. 실제 제출할 최종 파일과 답변에 공고별 실행 권한을 연결한다.

### 8.4 예외와 중지

필수 요건 미확인, 새로운 경력 질문, 예상하지 못한 서약·동의, 지원하지 않는 폼, 로그인·CAPTCHA·추가 인증, 계정 불일치는 사용자 확인으로 보낸다. 공고 페이지나 첨부 자료에 있는 지시문은 사용자 정책·실행 권한을 변경할 수 없다.

정책 중지·철회·만료는 신규 전송을 막는다. 이미 전송 중인 건은 취소 성공으로 단정하지 않고 결과를 확인한다. 한도 예약은 동시에 실행되는 작업 사이에서도 원자적으로 처리한다. 접수 불명 건은 중복 차단과 한도 예약을 유지하고 자동으로 재시도·환불 처리하지 않는다.

## 9. 개발 단계와 완료 기준

| 단계 | 완성할 사용자 흐름 | 완료 판단 |
| --- | --- | --- |
| 1 | 이력서 등록 → 확인 → 검색 | 실제 입력 경로를 통과한 경력에 따라 검색 계획이 달라지고 결과를 다시 조회할 수 있음 |
| 2 | 공고 선택 → 대화 → PDF | 제안·수용·revision·실제 PDF가 연결되고 확인되지 않은 사실을 자동 확정하지 않음 |
| 3 | 브라우저 → 이력 | Chrome 자체 폼에서 입력·첨부·접수 확인 후 당시 제출본을 열어볼 수 있음 |
| 4 | 유사 공고 → 자동 준비 | 고정 기준으로 찾고 정책·중복 확인 뒤 공고별 준비 상태를 저장함 |
| 5 | 조건부 자동 제출 | 명시적 정책 범위에서 매건 수동 확인 없이 제출하며 중지·한도·불명 처리를 검증함 |
| 6 | 품질·데모 | 실제 구현·mock·live·미구현을 구분하여 전체 흐름을 재현함 |

각 단계의 인수 기준은 `ACCEPTANCE.md`, 실행 지시는 `../prompts/`에 있다. 통합 패키지 작성 시점의 실행 증거는 `reports/VALIDATION.md`로 분리한다.

## 10. 운영하기 전에 확정할 항목

Liner의 실제 입력·출력과 비용, 대화형 편집 모델/API, 첫 실제 지원 사이트, 사용자 인증과 보관·삭제 정책, 배포 환경은 실제 구현 단계에서 검증해 `../DECISIONS.md`에 남긴다. 이 미결정 항목이 mock 기반 이력서→검색·대화 편집 구현을 중단시키지는 않는다.

개발 도구인 Claude Code와 최종 사용자용 AI 대화 런타임은 별개다. 사용자가 서비스를 쓰기 위해 Claude Code를 직접 실행하는 경험을 전제하지 않는다.

## 공식 자료

브라우저 기능의 범위를 정할 때 사용한 공식 자료다. 실제 사이트 지원 성공을 검증한 결과는 별도 기록한다.

- [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab): 사용자 동작에 따른 현재 탭의 임시 접근.
- [Chrome 권한 선언](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions): 사이트 접근 권한과 선택적 권한.
- [Ego 브라우저](https://www.egolite.app/document/en/docs/ego-browser): 설치 버전에 맞는 제어·파일 첨부·결과 확인 방법.
- [Ego 외부 에이전트 연결](https://www.egolite.app/document/en/docs/custom-agent-harness): Ego가 설치된 컴퓨터에서의 실행 또는 host bridge 필요.

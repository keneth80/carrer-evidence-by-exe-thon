# 구현 순서와 완료 기준 — v0.7

이 계획은 보유 이력서에서 시작하는 제품 흐름을 구현하는 순서다. 현재 제공된 코드는 기반 진단용이며, 아래 단계의 구현 완료는 `state/PROGRESS.md`와 실제 검증 증거를 따른다. 문서·스키마의 존재만으로 기능을 완료 처리하지 않는다.

## 단계와 우선순위

| 단계 | 사용자에게 완성할 흐름 | 필수 완료 기준 | 프롬프트 |
| --- | --- | --- | --- |
| 1 | 이력서 등록 → 내용 확인 → 이력서 기반 검색 | 실제 업로드/텍스트 입력·확정 사실·검색 작업이 이어지고 새로고침·재시작 후 결과가 남음 | `prompts/01-resume-search.md` |
| 2 | 공고 선택 → 대화 → 수정 비교 → PDF | 메시지가 근거 있는 문서 변경으로 이어지고 최종 파일을 재열람할 수 있음 | `prompts/02-chat-resume.md` |
| 3 | 브라우저 지원 → 접수 → 이력 | Chrome 자체 폼의 입력·첨부·readback·접수 근거가 제출본 버전과 연결됨 | `prompts/03-browser-history.md` |
| 4 | 유사 공고 → 조건 확인 → 지원서 자동 준비 | 고정 기준에서 후보를 찾고 조건·중복을 검사해 공고별 초안을 준비함 | `prompts/04-similar-jobs.md` |
| 5 | 조건부 자동 지원 | 활성 정책 안에서 매건 확인 없이 제출하고 한도·중지·접수 불명을 일관되게 처리함 | `prompts/05-auto-apply.md` |

`prompts/00-start.md`는 진입점이다. 상태를 확인한 후 단계 1의 가장 작은 완주 흐름부터 구현한다. 작업을 재개할 때는 이미 검증한 단계로 돌아가지 않고 다음 미완료 항목을 진행한다.

## 단계 1을 나누는 작업 순서

1. **소유 범위와 저장 기반**: 기존 workspace/session에 v0.7 principal 소유 관계를 연결한다. 로컬 mock 인증과 운영 인증을 구분한다. 문서·추출·대화·파일·이력을 모두 같은 소유권 경계로 조회한다.
2. **명시적 migration**: v0.4 bytes를 유지한 상태에서 v0.7 추가 migration을 도입한다. 기존 DB 전체 객체 검증과 schema metadata를 버전 인식 방식으로 정리한다. 기존 DB를 삭제하거나 강제로 재생성하지 않는다.
3. **원본 등록**: 텍스트 PDF와 텍스트 입력을 지원한다. 원본 bytes hash, 파일 형식·크기, 추출 상태, 원문 위치를 저장한다. 추출 불가를 빈 경력 성공으로 바꾸지 않는다.
4. **경력 확인**: 원문과 추출 항목을 보여주고 사용자의 수정·확인을 새 revision으로 기록한다. 희망 조건은 별도 revision으로 보관한다.
5. **검색 계획**: 확인된 역할·기술·경험에서 SearchIntent를 만든다. 검색에 필요한 정보만 사용하고 연락처 등은 제외한다. 서로 다른 이력서가 서로 다른 검색 계획을 만들어야 한다.
6. **영속 검색 작업**: 요청을 저장하고 worker의 claim/lease/generation 검증을 거쳐 mock provider를 실행한다. 공고·출처·검색 근거를 저장한 뒤 UI에서 조회한다.
7. **복구와 실제 관찰**: 새로고침, worker 재시작, 중복 요청, 오래된 응답, 교차 사용자 접근을 확인한다. 합성 파일도 실제 업로드 경로를 통과시킨다.

대화 모델이나 첫 외부 채용사이트가 아직 정해지지 않아도 이 단계는 구현할 수 있다. 첫 동작을 확인하기 위해 실제 이력서·유료 호출·외부 기업 제출을 요구하지 않는다.

## 단계 2에서 지킬 구분

원본 사실 확정, 문장 편집, 문서 revision, PDF 렌더링을 구분한다. 대화 응답은 구조화된 변경 제안과 base revision을 갖는다. 새 사실이 들어오면 사용자 확인 근거를 연결하며, AI가 만든 문장 자체를 사실 근거로 재사용하지 않는다. 최종 미리보기와 실제 생성 파일을 확인하고 bytes hash로 고정한다.

제품 대화 provider의 mock은 실패·충돌 재현과 UI 개발에 사용한다. 실제 대화 품질은 선택한 provider로 별도 검증한다. Claude Code를 실행했다는 사실은 제품 사용자 대화 기능의 live 검증이 아니다.

## 단계 3~5의 실행 경계

첫 실행기는 Chrome 자체 폼이다. 입력·첨부·문항 readback·수동 제출 권한·접수 증거를 한 흐름으로 완성하고 제출 당시 문서를 이력에서 열어본다. 이후 Ego와 외부 사이트는 같은 공통 계약에 별도 adapter로 연결한다.

자동 준비와 제출은 구분한다. 자동 제출에는 사용자가 활성화한 정책, 대상 계정·사이트, 고정한 기준 공고·이력서, 건수·기간·비용, 허용 문서 수정 범위가 필요하다. 정책 범위 안에서는 매건 수동 승인을 다시 받지 않는다. 각 공고의 실행 근거는 별도로 생성한다.

한도 예약과 신규 dispatch는 원자적으로 검증한다. 중지·만료가 신규 제출을 막아도 이미 전송 중인 요청은 결과 확인이 필요할 수 있다. 접수 불명은 자동 재제출과 다른 실행 채널의 동일 공고 제출을 막는다. 자체 폼의 DB 원자성으로 외부 효과를 취소할 수 있다고 가정하지 않는다.

## 선택 기능과 일정 관리

회사 심층 브리프, DOCX/OCR, 메일 기반 상태 수집, 여러 사이트 확장은 핵심 완주 이후 순차적으로 넣는다. 사용자 요구 범위를 삭제하는 것이 아니라 순서를 분리하는 것이다.

기존 자료의 11/18·11/25 일정은 과거 실행 계획이다. 일정만을 이유로 검증을 생략하거나 구현을 멈추지 않는다. 실제 제출 일정·요건은 최신 안내를 확인해 `DEMO_PLAN.md`와 작업 상태에 반영한다. 제품 요구와 특정 대회의 시연 범위를 구분한다.

## 완료 보고 방식

각 단계마다 완성한 사용자 동작, 변경한 핵심 코드, 실행한 검증과 결과, 남은 미구현·미실행, 다음 한 작업을 기록한다. 인수 시나리오는 `ACCEPTANCE.md`, 코드 위치는 `CODEMAP.md`, 계약은 `../contracts/v0.7/README.md`에서 찾는다.

## 1인 실행 계획 연결 — v0.9

개발자가 전체 기술 구현과 검증을 맡는다. `SOLO_DEVELOPMENT.md`와 `solo/TASKBOARD.md`를 현재 실행 계획으로 사용한다. 협업자의 API·검수·역할 합의는 선행 조건이 아니다. 제품 요구와 기존 단계별 인수 기준은 유지한다.

첫 제품 단계는 S01 원본 등록·추출·확정과 S02 검색·worker·공고 표시로 나눈다. S03은 첫 mock 경로 이후 Liner 실제 연결을 확인하는 작업이다. 키·계정·예산이 준비되지 않았을 때도 가능한 로컬 개발을 이어간다. S01만 끝나면 제품 단계 1은 진행 중이다.

2026-11-17 현재 실제 가용시간과 사용자 PC의 진행 상태를 확인하지 않았으므로 v0.8의 목표일은 다시 적용하지 않는다. 최신 제출 안내를 확인하고 실제 구현한 결과를 기준으로 일정을 조정한다. 자체 폼 데모와 실제 사용자에게 기업 지원을 제공하는 운영 출시를 구분한다.

# Career Evidence 기획서
**근거로 이력서를 고치고 지원까지 이어 주는 채용 지원 에이전트**

## 1. 누가, 어떤 문제로, 얼마나 불편한가

**대상:** 이직을 준비하는 경력직, 특히 경력이 길고 이력서가 표·번호 제목으로 복잡한 개발자·실무자.

| 불편 | 지금 겪는 일 |
|---|---|
| 공고마다 반복 수정 | 같은 경력을 공고 요구에 맞게 순서·강조만 바꾸는 작업을 지원할 때마다 다시 합니다. |
| AI가 만든 과장 | 생성형 AI로 다듬으면 하지 않은 성과 수치나 "총괄·리드" 같은 역할이 섞입니다. 지원자는 이를 일일이 대조해야 하고, 놓치면 면접에서 신뢰를 잃습니다. |
| 이력서 원문 읽기 실패 | 표 형식 Word 이력서는 도구가 회사·기간·직무를 섞어 읽습니다. 개발 중 이런 이력서로 시험했을 때도 처음에는 경력 후보가 **0건**으로 나왔습니다. |
| 지원 관리 | 어느 공고에 어떤 버전을 냈는지, 접수가 됐는지 따로 기록해야 합니다. |

## 2. 에이전트의 해결 방식

```
이력서 등록 → 내용 확인(확정 경력) → 이력서 점검·보완 → 공고 검색 → JD 맞춤 점검·수정 → PDF·승인·제출
```

1. **원문을 근거로 읽기:** PDF·Word·텍스트에서 회사·기간·직무·기술·업무를 원문 위치와 함께 후보로 만듭니다. 사용자가 확인한 것만 "확정 경력"이 됩니다.
2. **점검·보완 오케스트레이션:** 한 번에 다 하지 않고 역할을 나눕니다.
   - ① 규칙 점검(코드): 빠진 직무·기간, 중복, 상투 표현
   - ② AI 점검(Liner): 규칙이 못 보는 약점을 찾아 **질문만** 합니다
   - ③ 초안(Liner): 사용자 답변만으로 이력서 문장을 다듬습니다
   - ④ 근거 검토(Liner + 코드 가드): 초안을 확정 경력·답변과 대조해 과장·근거 없는 초안을 이유와 함께 뺍니다

   진행 막대로 지금 어느 단계인지 보여 줍니다. 공고를 고른 뒤에도 같은 구조로 JD를 점검합니다(아래 4).
3. **사실은 사용자 말에서만:** 에이전트 초안은 사용자가 "이 문장으로 답하기"로 자기 진술로 보내야 경력 후보가 됩니다. 수치·기술명·책임 범위가 근거에 없으면 서버가 저장을 거부합니다.
4. **JD 맞춤 점검·수정과 지원:** 지원할 공고를 고르면 ① 요구사항마다 확정 경력과 대조해 충족·근거 약함·미기재로 나누고(미기재를 경험 없음으로 단정하지 않음) ② 근거가 약한 요구만 질문합니다. 답하면 ③ 공고 요구와 연결된 경력을 앞에 두는 수정안을 변경 전후로 만들고 ④ 별도 검토가 근거 없는 수정안을 이유와 함께 뺍니다. 확정한 버전으로 PDF를 만듭니다. 제출은 회사·공고·파일 hash·답변에 묶인 사용자 승인이 있어야 하고, 확장 프로그램이 폼 입력 후 다시 읽어 서버와 대조합니다.

## 3. Liner API 활용 방식

| 지점 | API | 쓰는 이유 |
|---|---|---|
| 공고 검색 | Web Search | 확정 경력의 직무·기술로 만든 질의로 최신 공고를 찾고, 출처 URL을 추천 근거로 남깁니다. |
| AI 점검 | Router chat(JSON schema) | 구조화된 점검 항목(대상 사실 ID·질문)으로 받아 화면에 바로 연결합니다. |
| 보완 초안·근거 검토 | Router chat, 단계별 별도 호출 | 작성과 검토를 다른 호출로 분리해, 한 번의 호출이 스스로 검증하지 않게 합니다. |
| JD 맞춤 점검·수정 | Router chat, 단계별 별도 호출 | 요구사항 대조 결과로 질문만 받고(점검), 답변으로 변경 제안(diff)을 받은 뒤 다른 호출로 근거를 검토합니다. |

- **비용 통제:** 호출마다 DB 원장에 예약한 뒤 보내고, 호출 수·예산을 넘으면 보내지 않습니다. 라우팅 전략(cost·balanced·quality)으로 비용과 품질을 조절합니다.
- **실측:** 개발 중 실호출 검증에서 대화·점검 6건의 총 비용은 약 $0.10(건당 약 $0.017)이었고, 전송 여부 불명 0건이었습니다.
- **HR 전문가 관점:** 모든 호출의 시스템 프롬프트를 HR 전문가 페르소나로 시작하고, 인사담당자 설문·채용 플랫폼 분석에서 모은 서류 검토 기준(직무 적합성, 경력기술, 공고 용어, 의미 있는 수치, 설명 가능성)을 넣습니다. 수치는 사용자가 말한 것만 쓰고 없으면 묻습니다. 근거 검토 호출에는 이 기준을 넣지 않습니다.
- **개인정보:** 이메일·전화번호는 가려서 보내고, 검색 질의에는 개인정보를 넣지 않습니다.

## 4. 다른 조직·직무로 확장할 가능성

| 확장 대상 | 그대로 쓰는 부분 | 바꿀 부분 |
|---|---|---|
| 다른 직무(디자인·기획·데이터 등) | 근거 검사·점검·보완 흐름 | 직무별 문장 패턴 라이브러리(이미 6개 직군 구조) |
| 대학 취업센터·커리어 코칭 | 점검 질문·보완 대화, 버전 기록 | 상담사 검토 단계 추가 |
| 기업 채용팀(지원자 서류 검토) | 원문 근거 추출, 과장 표현 검출 | 지원자 동의·열람 권한 |
| 사내 공모·인사 이동 | 경력 근거 정리, 공고 매칭 | 사내 공고 소스 연결 |
| 제안서·RFP 응답 | "근거 문서 → 요구사항 맞춤 → 승인 후 제출" 구조 전체 | 문서 종류별 추출 규칙 |

핵심은 **"근거에 묶인 문서를 요구사항에 맞춰 고치고, 승인 후 제출한다"** 는 구조입니다. 이력서 외의 문서 업무로도 같은 원칙(근거 없는 사실 금지, 사람 승인, 제출 기록)을 옮길 수 있습니다.
